## Xianyu Feature Surface（闲鱼可观察功能面）

说明：这里不试图穷举“闲鱼全部功能”，只定义“抓包可证据化”的功能面——即能够通过关键页面/交互在网络层观察到请求，并可进一步封装为 API 或 MCP 工具的能力。

- 商品发布/编辑
  - 发布前校验（类 prepublish_check）
  - 获取预置参数（类 preget）
  - 上传图片/视频素材并写入发布 payload
  - 直接发布 / 编辑保存 / 编辑并重发布
  - 上下架、标记售出/删除（需抓包确认是否存在对应请求与权限限制）
- 会话与消息
  - 会话列表、历史消息分页
  - 发送：文本、图片、语音、视频（需抓包确认 contentType 与 payload）
  - 消息回执/已读、撤回、屏蔽/拉黑（是否可观察/可封装以抓包为准）
- 账号与风控
  - Cookie/Token 刷新、设备指纹相关字段（只做观察，不在抓包报告中记录敏感值）
- 多媒体与资源管理
  - 图片上传网关链路
  - 视频上传链路（通常不同 endpoint，可能分片/转码/回调）

## Gap → Candidate Features（差距到候选新增功能）

这部分先给“第一版候选”，后续以抓包证据校正字段与可行性（特别是视频/语音）。

### P0（高价值 + 与现有实现强相关）

- send_audio_message（语音消息发送）
  - 证据：WS 层存在明确 TODO（音频分支未实现）
  - 落地形态：upload_media（或音频专用上传）+ WS send_msg payload
  - 受限点：必须通过抓包确认 payload 字段/类型枚举
- listen_messages / auto_reply_worker（常驻监听与自动回复 worker）
  - 证据：README 明确列为未 MCP 化
  - 落地形态：独立进程/脚本，复用现有 WS 客户端；MCP 仍保持短调用（避免常驻循环塞进 MCP 主进程）

### P1（高价值但依赖新链路证据）

- upload_video / send_video_message（视频上传与视频消息发送）
  - 原因：通用上传网关可能拒绝 mp4；视频通常需要专用链路（可能含分片与转码）
  - 先决条件：抓包拿到可复现实例（endpoint、参数、签名/鉴权方式、响应结构）

### P2（增强型工具与可观测性）

- upload_media 增强：失败原因结构化输出（如 TYPE_NOT_CONFIRMED）+ 更明确的“图片/视频不兼容”提示
- 暴露 ItemApi 原语：prepublish_check / preget（用于上层自动化构造 payload 与诊断失败原因）

## Browser Automation Plan（抓包执行计划）

### 总体策略

以“关键页面 + 关键交互”为驱动，让浏览器产生真实网络请求；对每个“候选功能”输出最小证据集：
- 请求：URL、method、关键 headers（脱敏）、query/body 结构（脱敏）、发起页面动作
- 响应：关键字段（脱敏）、错误码与含义
- 可复现性：哪些字段是必须动态生成、是否依赖签名/mtop token/设备信息

### 抓包范围与路径（建议顺序）

1) 商品发布/编辑页（PC Web）
- 打开：发布页/编辑页
- 动作：进入发布、上传素材、提交/校验（尽量不真正发布，优先触发校验/预检）
- 目标：定位 prepublish_check/preget/edit/publish 的请求形态与参数结构

2) 会话页（PC Web）
- 动作：打开会话列表、进入会话、发送文本/图片
- 目标：定位 list conversations/messages 与 send message 的请求形态；观察是否存在语音/视频入口与请求

3) 视频上传链路（若 PC Web 无入口）
- 预期：PC Web 可能没有视频入口；此时抓包目标转为“确认缺失”，并在报告中记录“Web 不具备该入口”的证据（UI/网络均缺失）
- 后续：如果需要 App 端链路，再单独设计移动端抓包方案（不在本次浏览器自动化范围内）

### 数据脱敏规范（必须）

- 不在文档中写入任何 Cookie、token、_m_h5_tk、sign、用户 uid/unb 等敏感值
- 抓包报告只保留字段结构与必要的非敏感常量（如 apiName、功能开关字段）
