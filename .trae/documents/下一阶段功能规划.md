# 下一阶段功能规划

## 概述

通过对项目代码、openspec 变更记录、以及三个上游参考项目（XianyuAutoAgent、xianyu-auto-reply、XianYuApis）的对比分析，识别出 22 项尚未实现的能力。本规划按"投入产出比"和"场景价值"两个维度筛选出推荐优先实施的 8 项功能，分为三个梯队。

## 现状分析

### 已实现能力

当前 MCP 层暴露 12 个工具，覆盖登录态管理、商品查询/上下架/发布、会话查询、主动发消息四条链路。

### 底层已封装但未暴露的能力

`third_party/pyxianyu` 中已存在但 MCP 层未暴露的能力：

- `ItemApi.edit_item()` — 商品编辑接口
- `ItemApi.prepublish_check()` / `preget()` — 发布前校验与预取
- `MediaApi.upload_media()` — 媒体上传（目前仅内部调用）
- `XianyuLive.main()` — 常驻 WebSocket 消息监听
- `message.make_audio()` — 语音消息类型（`send_msg` 中 audio 分支标注 TODO）

### 已有 openspec 规划

- `edit-item-tool`：商品编辑工具，推迟到有可测试实体商品后实施
- `publish-physical-item`：已实现 MCP 工具，Task 6（实际发布测试）未完成
- `remove-nodejs-dependency`：纯 Python 签名，Task 4.2/4.3 验证未完成

### 参考项目的核心差距

- XianyuAutoAgent：常驻监听 + LLM 自动回复 + 议价系统 + 上下文管理
- xianyu-auto-reply：订单管理 + 自动发货 + 自动评价 + 批量发布 + 多账号
- XianYuApis：扫码登录（纯 HTTP）+ Cookie 风控处理

## 推荐功能（按优先级排序）

### 第一梯队：底层已就绪，仅需 MCP 暴露

#### 1. edit_item — 商品编辑工具

**价值**：补全商品管理闭环（发布 → 编辑 → 下架 → 重上架），是商品运营的基础能力。

**现状**：底层 `ItemApi.edit_item()` 已完整实现（`apis/item_api.py:219`），openspec 已有完整规划（`openspec/changes/edit-item-tool/`），前置条件是有一件可测试的实体商品。

**实施方案**：
- 在 `XianYuApiTools` 中新增 `edit_item` 方法，支持两种模式：
  - 快速编辑：`item_id` + `overrides`（内部走 `get_item_edit_detail` → `build_reshelf_payload` → 覆盖字段 → `edit_item`）
  - 直接编辑：`item_id` + `payload`（直接提交完整 payload）
- 在 `server.py` 中注册工具，注明仅对实体商品有效
- 完成已有 openspec 规划的 Task 1-3

**涉及文件**：`src/xianyu_mcp/tools/xianyu_api_tools.py`、`src/xianyu_mcp/server.py`

#### 2. upload_media — 独立媒体上传工具

**价值**：当前媒体上传仅在 `send_image_message` 和 `publish_physical_item` 内部调用，独立暴露后可用于头像更换、素材管理等场景，也为后续语音消息发送做铺垫。

**现状**：底层 `MediaApi.upload_media()` 已完整实现（`apis/media_api.py:15`），支持 jpg/jpeg/png/webp 格式。

**实施方案**：
- 在 `XianYuApiTools` 中新增 `upload_media` 方法，接受本地路径或 http/https URL，返回上传后的图片 URL 和尺寸信息
- 复用现有 `_prepare_image` 方法处理 URL 下载和路径解析
- 在 `server.py` 中注册为只读工具（上传不修改商品状态）

**涉及文件**：`src/xianyu_mcp/tools/xianyu_api_tools.py`、`src/xianyu_mcp/server.py`

#### 3. prepublish_check / preget — 发布前检查工具

**价值**：在发布或编辑商品前预检，提前发现风控限制或参数缺失，提升 `publish_physical_item` 和 `edit_item` 的成功率。

**现状**：底层 `ItemApi.prepublish_check()`（`apis/item_api.py:156`）和 `preget()`（`apis/item_api.py:176`）均已实现。

**实施方案**：
- 封装为两个独立 MCP 工具，或合并为一个 `check_publish_readiness` 工具
- `prepublish_check` 返回当前账号是否可发布、有哪些限制
- `preget` 返回发布/编辑所需的预置参数（分类树、运费模板等）

**涉及文件**：`src/xianyu_mcp/tools/xianyu_api_tools.py`、`src/xianyu_mcp/server.py`

### 第二梯队：核心场景，中等开发量

#### 4. 扫码登录

**价值**：解决当前手动从浏览器复制 Cookie 的最大痛点。新用户上手成本高，Cookie 失效后需重新手动获取。扫码登录可实现全自动登录态获取。

**现状**：上游 XianYuApis 已有纯 HTTP 实现（无需 Playwright），完整流程包括：`build_initial_cookies()` → passport 加载 → `generate.do` 获取二维码 → 轮询 `query.do` → `login_token/login.do` 完成登录。当前 `third_party/pyxianyu` 中 `XianyuClient` 已有 `reset_login_info_url`（`core/client.py:37`）但未接入。

**实施方案**：
- 在 `third_party/pyxianyu/apis/auth_api.py` 中新增 `qrcode_login` 方法
- 在 MCP 层新增 `start_qrcode_login`（获取二维码）和 `check_qrcode_login`（轮询登录状态）两个工具
- 登录成功后自动更新 `.env` 中的 Cookie
- 需考虑终端二维码展示方式（ASCII art 或返回二维码 URL）

**涉及文件**：`third_party/pyxianyu/apis/auth_api.py`、`src/xianyu_mcp/tools/xianyu_api_tools.py`、`src/xianyu_mcp/server.py`

#### 5. 语音消息收发

**价值**：补全消息类型，当前只支持文本和图片。语音消息在闲鱼交易沟通中是常见场景。

**现状**：`message/types.py` 已定义 `AudioContent` 和 `make_audio()`，但 `goofish_live.py:206` 的 `send_msg` 中 audio 分支标注 `TODO`。

**实施方案**：
- 在 `goofish_live.py` 的 `send_msg` 中完成 audio 分支：上传语音文件 → 获取 URL → 构造 WebSocket 协议消息
- 在 MCP 层新增 `send_audio_message` 工具
- 需研究闲鱼语音消息的 WebSocket 协议格式（contentType、custom type 值）

**涉及文件**：`third_party/pyxianyu/goofish_live.py`、`src/xianyu_mcp/tools/xianyu_api_tools.py`、`src/xianyu_mcp/server.py`

#### 6. 常驻消息监听 + 自动回复框架

**价值**：这是闲鱼自动化的核心场景。当前只能主动查询消息，无法实时接收和自动回复。XianyuAutoAgent 的核心价值就在于此。

**现状**：底层 `XianyuLive.main()` 已有常驻监听框架（`goofish_live.py:300`），心跳保活和 Token 自动刷新也已实现，但 `handle_message` 仅是 echo 示例。

**实施方案**（分两步）：

**步骤 A：常驻监听 + 事件通知**
- 将 `XianyuLive.main()` 封装为独立进程或后台任务（参考 README 已有建议：消息监听与 MCP 短调用拆成两个进程）
- 设计事件通知机制：监听到新消息后，通过回调、webhook、或 SSE 推送给 MCP 客户端
- 从 WebSocket 消息中识别订单状态变化（"等待买家付款"/"交易关闭"/"等待卖家发货"）

**步骤 B：自动回复 Worker**
- 接入 LLM（DeepSeek/豆包，符合用户偏好）
- 实现意图分类 → 议价/技术/默认多专家路由
- SQLite 上下文管理（按 `cid + item_id` 维度）
- 安全过滤（屏蔽微信/QQ/支付宝等敏感词）
- 人工接管模式（关键词切换、超时自动恢复）

**涉及文件**：新建 `src/xianyu_mcp/listener.py`（监听进程）、`src/xianyu_mcp/reply_worker.py`（自动回复），修改 `goofish_live.py`

### 第三梯队：需逆向新 API，开发量较大

#### 7. 订单查询

**价值**：当前无法查看订单状态，卖家需要切换到 App 或网页端查看。订单查询是实现自动发货、自动评价等高级功能的前置依赖。

**现状**：三个参考项目中 xianyu-auto-reply 实现了订单拉取，但订单 API 端点未公开，需独立逆向。

**实施方案**：
- 抓包分析闲鱼 PC 端订单列表接口（推测为 `mtop.taobao.idle.order.list` 类接口）
- 在 `ItemApi` 或新建 `OrderApi` 中封装订单查询方法
- MCP 层新增 `list_orders`（订单列表）和 `get_order_detail`（订单详情）工具

**涉及文件**：新建 `third_party/pyxianyu/apis/order_api.py`、`src/xianyu_mcp/tools/xianyu_api_tools.py`、`src/xianyu_mcp/server.py`

#### 8. 商品删除

**价值**：当前只有下架（`downshelf_item`），下架后商品仍存在于账号中。删除功能可彻底清理不需要的商品，配合定时规则实现商品自动轮换。

**现状**：xianyu-auto-reply 实现了删除规则，但删除 API 端点需逆向。

**实施方案**：
- 抓包分析闲鱼 PC 端商品删除接口
- 在 `ItemApi` 中新增 `delete_item` 方法
- MCP 层新增 `delete_item` 工具

**涉及文件**：`third_party/pyxianyu/apis/item_api.py`、`src/xianyu_mcp/tools/xianyu_api_tools.py`、`src/xianyu_mcp/server.py`

## 假设与决策

1. **优先级依据**：第一梯队选择"底层已就绪、仅需 MCP 暴露"的功能，投入产出比最高；第二梯队选择"核心场景痛点"，即用户最急需但开发量适中的功能；第三梯队是"需逆向 API"的功能，风险和成本都较高
2. **自动回复架构**：参考 README 已有建议，将消息监听和 MCP 短调用拆成两个进程，不在 MCP 主进程中跑常驻循环
3. **LLM 选型**：用户偏好国产 AI 模型（DeepSeek、豆包），自动回复 Worker 优先接入这两个
4. **扫码登录实现方式**：优先采用纯 HTTP 实现（参考上游 XianYuApis），不引入 Playwright 等浏览器自动化依赖
5. **未列入推荐的功能**：多账号管理（架构改动大）、批量发布（依赖素材库系统）、返佣子系统（业务复杂度高）等企业级功能不在当前阶段推荐

## 验证方式

每个功能实现后，按以下方式验证：

1. **edit_item**：用一件实体商品测试快速编辑（改标题、价格）和直接编辑模式
2. **upload_media**：上传本地图片和 URL 图片，确认返回有效 URL 和尺寸
3. **prepublish_check/preget**：调用后确认返回当前账号发布限制和预置参数
4. **扫码登录**：完整走通二维码生成 → 扫码 → 登录成功 → Cookie 写入 `.env` → 后续工具调用正常
5. **语音消息**：发送一条语音消息，确认对方能正常收到
6. **常驻监听**：启动监听进程，从另一个账号发消息，确认能实时收到通知
7. **自动回复**：监听到消息后 LLM 自动回复，确认回复内容合理、无敏感词泄露
8. **订单查询**：拉取订单列表，确认订单状态与 App 端一致
9. **商品删除**：删除一件已下架商品，确认从商品列表中消失
