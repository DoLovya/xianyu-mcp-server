## Context

当前 MCP 服务直接调用 `third_party/pyxianyu` 的接口封装。读/写请求缺少统一的节流、抖动与风控失败后的止损机制，导致在连续调用写操作（例如 `edit_item → downshelf_item → reshelf_item`）后容易触发 `FAIL_SYS_USER_VALIDATE`，从而使服务整体不可用并需要人工恢复 Cookie。

约束：
- 不引入新的第三方依赖（优先使用标准库）
- 不改变各工具的核心业务语义，只在“何时请求/是否请求”上增加护栏
- 不输出任何敏感信息（Cookie/token）

## Goals / Non-Goals

**Goals:**
- 在 MCP 工具层引入统一的请求护栏：READ/WRITE 分级限速、随机抖动、WRITE 串行
- 对可疑失败进行指数退避；对强风控信号进行熔断与冷却
- 护栏参数可通过环境变量配置，默认值偏保守且开箱可用

**Non-Goals:**
- 规避或对抗闲鱼风控策略本身
- 自动完成 `punish` 验证或验证码流程
- 在服务端持久化风控状态（仅进程内状态）

## Decisions

### Decision: 护栏接入点
在 `XianYuApiTools` 的每个 MCP 工具方法中，在调用具体 API 前统一执行护栏逻辑。

备选方案：
- 在 `pyxianyu` 的 `XianyuClient` 低层统一拦截所有 HTTP 请求：覆盖范围更大但侵入第三方代码，且难以按“工具语义”区分 READ/WRITE
- 在 MCP `server.py` 中做装饰器：可行，但需要对每个工具显式包裹，且仍需识别 READ/WRITE 并支持基于参数的串行键

选择理由：
- `XianYuApiTools` 是本仓库对外工具能力的聚合层，最适合表达“工具级”护栏
- 无需修改第三方子仓库，风险更可控

### Decision: 状态管理与并发模型
使用进程内状态：
- 最近一次 READ/WRITE 请求时间戳
- 连续可疑失败计数
- 熔断冷却截止时间戳

并发模型：
- WRITE 全局串行（同一进程内）
- 可扩展：对 item/cid 维度的细粒度串行键，但第一版以全局 WRITE 串行即可显著降低风险

### Decision: 错误分类
通过对异常类型与返回的 `ret` 字段（或错误码字符串）进行分类：
- 强风控信号：`FAIL_SYS_USER_VALIDATE`（触发熔断冷却）
- 可疑失败：网络异常、5xx、或可配置的风控/限流类错误（触发指数退避）
- 业务错误：例如参数校验失败（不触发退避/熔断）

## Risks / Trade-offs

- 限速会降低吞吐 → 提供环境变量可调；默认偏保守
- 进程内状态在服务重启后丢失 → 可接受（目标是“减少触发”，不是持久化风控治理）
- 错误分类不完备 → 默认仅对最明确的信号做熔断；其余走退避保守处理
